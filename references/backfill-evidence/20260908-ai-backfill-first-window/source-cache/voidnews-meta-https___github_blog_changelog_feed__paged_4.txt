		<title>Global model policy generally available</title>
		<link>https://github.blog/changelog/2026-08-26-global-model-policy-generally-available</link>
		
		<dc:creator><![CDATA[Allison]]></dc:creator>

					<description><![CDATA[<p>In July, we announced a default model policy for generally available GitHub Copilot models on Copilot Business and Copilot Enterprise plans. Starting today, we&#8217;re gradually rolling out enforcement of the&#8230;</p>
<p>The post <a href="https://github.blog/changelog/2026-08-26-global-model-policy-generally-available">Global model policy generally available</a> appeared first on <a href="https://github.blog">The GitHub Blog</a>.</p>
]]></description>
										<content:encoded><![CDATA[<!DOCTYPE html PUBLIC "-//W3C//DTD HTML 4.0 Transitional//EN" "http://www.w3.org/TR/REC-html40/loose.dtd">
<html><body><p>In July, we announced a default model policy for generally available GitHub Copilot models on Copilot Business and Copilot Enterprise plans. Starting today, we&rsquo;re gradually rolling out enforcement of the policy through September 1, so it will take effect at different times for different enterprises. Previously unconfigured and new generally available models will inherit the global policy state. Administrators can make durable decisions for individual models at their discretion. Open-weight models and any models that require data retention are disabled by default.</p>
<h2 id="whats-changing" id="whats-changing" ><a class="heading-link" href="#whats-changing">What&rsquo;s changing<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>Once the policy takes effect for your organization or enterprise:</p>
<ul>
<li>Models you haven&rsquo;t previously configured will change their state to &ldquo;Delegate to default policy&rdquo;, and they&rsquo;ll begin following your policy setting. If your policy is enabled &mdash; which is the default &mdash; those models will become available to your users. </li>
<li>&ldquo;Delegate to default policy&rdquo; is a live, dynamic state that always tracks your policy. You can change the policy at any time, and all applicable models follow that state change.</li>
<li>We always preserve explicit choices. If you&rsquo;ve deliberately enabled or disabled a specific model, we do not change that setting.</li>
<li>We exclude open-weight models (e.g., DeepSeek and Kimi K2) and models not covered by GitHub&rsquo;s data retention agreement (e.g., Fable 5) from default enablement, regardless of your policy.</li>
</ul>
<p>After the rollout, each model in your settings shows one of four states:</p>
<ul>
<li><strong>Enabled:</strong> You&rsquo;ve explicitly turned the model on.</li>
<li><strong>Disabled:</strong> You&rsquo;ve explicitly turned the model off.</li>
<li><strong>Delegate to enterprise teams/apps or organizations:</strong> The model follows a setting inherited from your enterprise team or organization.</li>
<li><strong>Delegate to default policy:</strong> The model follows your default enablement policy.</li>
</ul>
<p>To learn more, see <a href="https://docs.github.com/enterprise-cloud@latest/copilot/concepts/models/default-availability">default model availability</a>.</p>
<h2 id="whats-next" id="whats-next" ><a class="heading-link" href="#whats-next">What&rsquo;s next<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>We are looking for your feedback in the community discussion below. We&rsquo;re evaluating making the global model policy state an explicit decision and removing the &ldquo;Delegate to default policy&rdquo; state. This would help ensure that every policy reflects an explicit, intentional choice rather than an inferred one.</p>
<p>Join the discussion within <a href="https://github.com/orgs/community/discussions/203163">GitHub Community</a>.</p>
</body></html>

		<link>https://github.blog/changelog/2026-08-26-github-apps-can-now-access-enterprise-billing-data</link>

					<description><![CDATA[<p>Enterprise owners can now grant a GitHub App access to enterprise billing data. When you create or configure a GitHub App, you can select the enterprise billing permission and choose&#8230;</p>
<p>The post <a href="https://github.blog/changelog/2026-08-26-github-apps-can-now-access-enterprise-billing-data">GitHub Apps can now access enterprise billing data</a> appeared first on <a href="https://github.blog">The GitHub Blog</a>.</p>

										<content:encoded><![CDATA[<!DOCTYPE html PUBLIC "-//W3C//DTD HTML 4.0 Transitional//EN" "http://www.w3.org/TR/REC-html40/loose.dtd">
<html><body><p>Enterprise owners can now grant a GitHub App access to enterprise billing data. When you create or configure a GitHub App, you can select the enterprise billing permission and choose one of two levels: read or read and write.</p>
<p>Previously, the only way to read usage or manage budgets and cost centers through the API was a personal access token belonging to an enterprise owner or billing manager. That tied your billing automation to one person&rsquo;s token, so it broke when that person changed roles or left.</p>
<p>Now an app installation access token that carries the enterprise billing permission can call the enterprise billing REST API endpoints. Use it to pull usage data into your finance and BI systems, reconcile invoices, and manage budgets and cost centers, all without relying on an individual&rsquo;s token. As an added benefit, you also get higher rate limits than a personal access token.</p>
<p>The enterprise billing permission is available on GitHub Enterprise Cloud. To learn more, see <a href="https://docs.github.com/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app">Choosing permissions for a GitHub App</a>.</p>

<html><body><p>The rule insights dashboard is now generally available at both the repository and organization levels. You get a visual, high-level view of how GitHub evaluates and enforces your GitHub repository rulesets, so you can spot trends and report on governance without stitching data together by hand.</p>
<h3 id="organization-level-dashboard" id="organization-level-dashboard" ><a class="heading-link" href="#organization-level-dashboard">Organization-level dashboard<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h3>
<p>The organization-level dashboard we shipped in public preview is now generally available. In your organization&rsquo;s <strong>Settings &gt; Repository</strong> tab, you get an aggregated view across every repository, which helps your governance and compliance teams report across the whole organization instead of individually checking each repository. At the organization level, you can:</p>
<ul>
<li>Review aggregated rule evaluation metrics for all repositories in your organization.</li>
<li>Identify your top repositories by bypasses to focus your review where it matters most.</li>
<li>Filter results by evaluation status, branch, ruleset, and date range to focus on the activity you care about.</li>
</ul>
<h3 id="repository-level-dashboard" id="repository-level-dashboard" ><a class="heading-link" href="#repository-level-dashboard">Repository-level dashboard<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h3>
<p>The repository-level dashboard we shipped in public preview is now generally available. In your repository&rsquo;s <strong>Settings &gt; Rules</strong> tab, you can see successes, failures, and bypasses over time, along with the most active bypassers for your rulesets. Each chart links back to the rule insights page with filters prefilled, so you can quickly drill into specific statuses, bypasses, or time ranges.</p>
<p><img decoding="async" src="https://github.com/user-attachments/assets/9befa788-af48-4a9c-965f-96264697f4de" alt="Rule insights dashboard showing rule suites performance with charts and counts for allowed, failed, and bypassed evaluations."></p>
<p>Whether you&rsquo;re responding to an incident or auditing bypass activity, the dashboard helps you spot trends at a glance and drill into the details when you need them.</p>
<h3 id="availability" id="availability" ><a class="heading-link" href="#availability">Availability<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h3>
<p>The rule insights dashboard is generally available at both the repository and organization levels, and you can export the data to CSV at either level for reporting and record keeping. To learn more, see <a href="https://docs.github.com/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets">our docs about GitHub repository rulesets</a>.</p>

										<content:encoded><![CDATA[<!DOCTYPE html PUBLIC "-//W3C//DTD HTML 4.0 Transitional//EN" "http://www.w3.org/TR/REC-html40/loose.dtd">
<html><body><p>You can now block a user directly from a security advisory page in public repositories owned by either an organization or a personal account. This brings the streamlined moderation experience available for issues and pull requests to security advisories.</p>
<p>Security advisories contain user-created content and, like other collaborative surfaces, can attract spam or abuse. Previously, addressing this required navigating to organization settings, personal settings, or the user&rsquo;s profile.</p>
<p>With this update, you can:</p>
<ul>
<li>Block a user from the three-dot menu in a security advisory description or comment without leaving the page.</li>
<li>Review a clear confirmation of what blocking the user means before taking action.</li>
<li>Keep the security advisory intact while removing the source of spam or abuse.</li>
</ul>
<p>In organization-owned repositories, only organization moderators or administrators can initiate a block. In personal account-owned repositories, the account owner can initiate a block.</p>
<p>Join the <a href="https://github.com/orgs/community/discussions/205714">Community discussion</a> to share your questions or feedback.</p>

		<link>https://github.blog/changelog/2026-08-25-push-rules-in-rulesets-now-support-path-exceptions</link>
		
		<dc:creator><![CDATA[Allison]]></dc:creator>

				<guid isPermaLink="false">https://github.blog/changelog/2026-08-25-push-rules-in-rulesets-now-support-path-exceptions</guid>

					<description><![CDATA[<p>You can now configure push rules more granularly by exempting specific file paths, so a rule applies everywhere in scope except the paths you choose. Path exceptions are in public&#8230;</p>
<p>The post <a href="https://github.blog/changelog/2026-08-25-push-rules-in-rulesets-now-support-path-exceptions">Push rules in rulesets now support path exceptions</a> appeared first on <a href="https://github.blog">The GitHub Blog</a>.</p>
]]></description>
										<content:encoded><![CDATA[<!DOCTYPE html PUBLIC "-//W3C//DTD HTML 4.0 Transitional//EN" "http://www.w3.org/TR/REC-html40/loose.dtd">
<html><body><p>You can now configure push rules more granularly by exempting specific file paths, so a rule applies everywhere in scope except the paths you choose. Path exceptions are in public preview.</p>
<p>Push rules give you strong control over what enters a repository. Sometimes a rule needs a narrow exception, and until now your options were to relax it for everyone or enforce it outside of GitHub. You can now keep the rule in place and exempt only the paths that need it.</p>
<h2 id="where-to-find-it" id="where-to-find-it" ><a class="heading-link" href="#where-to-find-it">Where to find it<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>When you configure either supported rule, expand <strong>Allowed exceptions</strong> and add the path patterns the rule should skip. GitHub validates your patterns when you save the ruleset, so you can fix mistakes right away.</p>
<p>Two push rules support exceptions today:</p>
<ul>
<li><strong>Restrict file paths:</strong> Block a file type across the repository while allowing it at a specific path, such as blocking JAR files everywhere except <code>**/gradle/wrapper/*.jar</code>.</li>
<li><strong>Restrict file size:</strong> Enforce a size limit while exempting paths that already exceed it, so you can adopt the limit without changing those files first.</li>
</ul>
<p>For pattern syntax and the full list of push rules, see <a href="https://docs.github.com/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets">available rules for rulesets</a>.</p>
<p>Join the <a href="https://github.com/orgs/community/discussions/categories/repositories">community discussion</a> to share feedback.</p>
</body></html>

<p>The post <a href="https://github.blog/changelog/2026-08-21-the-new-github-copilot-experience-in-slack">The new GitHub Copilot experience in Slack</a> appeared first on <a href="https://github.blog">The GitHub Blog</a>.</p>

										<content:encoded><![CDATA[<!DOCTYPE html PUBLIC "-//W3C//DTD HTML 4.0 Transitional//EN" "http://www.w3.org/TR/REC-html40/loose.dtd">
<html><body><p>The GitHub integration in Slack now brings the agentic capabilities of GitHub Copilot CLI and the GitHub Copilot app into Slack in public preview. You can work with <code>@GitHub</code> to plan changes, investigate problems, and hand off coding tasks from the conversations where your team coordinates work. GitHub is also a launch partner for Slack Code, a new type of channel designed for agents.</p>
<p>Bringing Copilot into the flow of conversation helps your team turn shared intent into shippable work.</p>
<h2 id="what-you-can-now-do-with-github" id="what-you-can-now-do-with-github" ><a class="heading-link" href="#what-you-can-now-do-with-github">What you can now do with @GitHub<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>Mention <code>@GitHub</code> in a direct message, channel, or thread to start an agent session. Copilot can use the conversation and permitted GitHub context to:</p>
<ul>
<li>Answer questions about your code and GitHub activity.</li>
<li>Triage bug reports, update existing issues, or create and label new issues.</li>
<li>Investigate failures, implement changes, and validate its work in a secure cloud sandbox.</li>
<li>Open a pull request and provide a link to the conversation for review.</li>
</ul>
<p>GitHub Copilot continues working asynchronously while you&rsquo;re in a meeting, commuting, or focused on something else. You can direct the session from Slack as it works, then continue from the pull request in your terminal, the GitHub Copilot app, or your IDE.</p>
<h2 id="slack-code-and-github-copilot" id="slack-code-and-github-copilot" ><a class="heading-link" href="#slack-code-and-github-copilot">Slack Code and GitHub Copilot<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>GitHub Copilot can also create a dedicated code channel that keeps the task focused without adding noise to the original conversation.</p>
<p>Inside the code channel, your team can follow the plan, inspect the diffs, review output previews like HTML artifacts, and iterate with Copilot. Anyone can join the channel from the original thread, add context, redirect the approach, or stop the session.</p>
<h2 id="the-power-of-multiplayer" id="the-power-of-multiplayer" ><a class="heading-link" href="#the-power-of-multiplayer">The power of multiplayer<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>Agent sessions in Slack are shared, so your team can collaborate on the work where the request began instead of one person working privately with an agent.</p>
<p>Working in the open also makes effective agent workflows easier to learn. Developers can see how their teammates prompt the agent and learn from each other. Issues and pull requests created from the conversation are attributed to the Copilot app identity, and actions remain bounded by existing GitHub permissions and controls.</p>
<h2 id="availability-and-getting-started" id="availability-and-getting-started" ><a class="heading-link" href="#availability-and-getting-started">Availability and getting started<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>The public preview is available to organizations on GitHub Copilot Business and GitHub Copilot Enterprise plans. Usage counts against your existing Copilot entitlements and can be managed with existing Copilot cloud agent budgets.</p>
<p>To get started:</p>
<ol>
<li>Make sure an administrator has enabled the Copilot cloud agent policy for your organization.</li>
<li>Install or upgrade the <a href="https://slack.com/marketplace/A01BP7R4KNY-github">GitHub app for Slack</a>.</li>
<li>Link your GitHub account and mention <code>@GitHub</code> in a conversation.</li>
</ol>
<p>Repository administrators can require an additional approval for any pull request attributed to the Copilot app identity before it can merge. Requiring an additional approval keeps a human in the loop before agent-authored work ships. Your team moves fast without losing compliance oversight.</p>
<p>For setup details and supported workflows, see <a href="https://docs.github.com/copilot/how-tos/use-copilot-agents/coding-agent/integrate-coding-agent-with-slack">how to use Copilot coding agent with Slack</a>.</p>

Mention <code>@GitHub</code> in a channel, thread, or direct message to start a GitHub Copilot cloud agent session. Anyone in the conversation can ask questions, add context, and help plan or steer the work. Participants with write access to the repository can trigger Copilot to make changes.</p>
<h2 id="turn-meeting-decisions-into-ready-work" id="turn-meeting-decisions-into-ready-work" ><a class="heading-link" href="#turn-meeting-decisions-into-ready-work">Turn meeting decisions into ready work<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>

<p><em>Editor&rsquo;s note (August 21, 2026): Updated the language to align with Teams terminology.</em></p>
<h2 id="continue-work-across-github-copilot-surfaces" id="continue-work-across-github-copilot-surfaces" ><a class="heading-link" href="#continue-work-across-github-copilot-surfaces">Continue work across GitHub Copilot surfaces<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>Start a task from Teams and let Copilot work asynchronously in a secure cloud sandbox. Follow progress in the channel thread, then continue working with the agent-generated artifacts from your terminal, the GitHub Copilot app, or your preferred IDE. For more information, see <a href="https://docs.github.com/copilot/concepts/about-cloud-and-local-sandboxes#cloud-sandboxing">our documentation about cloud sandboxing</a>.</p>
<h2 id="availability-and-getting-started" id="availability-and-getting-started" ><a class="heading-link" href="#availability-and-getting-started">Availability and getting started<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>The public preview is available with paid GitHub Copilot plans. GitHub Copilot cloud agent sessions started in Microsoft Teams consume AI credits. For organizations, cloud agent AI credit usage is governed by <a href="https://docs.github.com/copilot/concepts/billing/usage-based-billing-for-organizations-and-enterprises">usage-based billing budgets</a>. Cloud sandbox usage is billed separately and can be controlled with a <a href="https://docs.github.com/billing/concepts/product-billing/cloud-and-local-sandboxes#managing-your-budget-for-cloud-sandboxes">product-level or SKU-level budget</a>.</p>
<p>To get started:</p>
<ol>
<li>For users in an organization or enterprise, make sure an administrator has enabled GitHub Copilot cloud agent and cloud sandboxes. Cloud sandbox policies share the same configuration as cloud agent policies.</li>
<li>Install the <a href="https://teams.microsoft.com/l/app/836ecc9e-6dca-4696-a2e9-15e252cd3f31">GitHub app for Microsoft Teams</a>.</li>
<li>In Teams, mention <code>@GitHub</code> and follow the prompts to connect your GitHub account.</li>
<li>For public channels, configure a default repository if prompted. Direct messages don&rsquo;t use a default repository.</li>
<li>Mention <code>@GitHub</code>, followed by your task. You can also use <code>@GitHub help</code> to see available commands.</li>
</ol>
<h2 id="maintain-compliance-oversight" id="maintain-compliance-oversight" ><a class="heading-link" href="#maintain-compliance-oversight">Maintain compliance oversight<span class="heading-hash pl-2 text-italic text-bold" aria-hidden="true"></span></a></h2>
<p>Repository administrators can now require an additional approval for any pull request attributed to the Microsoft Teams Copilot integration identity before it can merge. If you require two approvals in a repository, with this enabled you will need three for Copilot-created pull requests. Requiring an additional approval keeps a human in the loop before agent-authored work ships. Your team moves fast without losing compliance oversight.</p>
<p>For setup details, permissions, repository and branch selection, and supported workflows, see <a href="https://docs.github.com/copilot/how-tos/copilot-integrations/integrate-cloud-agent-with-teams">how to integrate GitHub Copilot cloud agent with Microsoft Teams</a>.</p>
