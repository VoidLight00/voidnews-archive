AI-Generated 3D Game Assets in Practice: How 3AGameFactory Uses Meshy for Image-to-3D

3AGameFactory's AI agent uses Meshy image-to-3D and text-to-3D to create engine-ready GLB characters and props for Unity, UE5, Blender, and three.js.

Bohan Zeng
Posted: September 9, 2026

3AGameFactory is an open-source framework from OpenDCAI at Peking University that uses an AI coding agent to turn a game requirement into AI-generated 3D game assets, gameplay, UI, and a playable build. Released under Apache 2.0, it targets UE5, Unity, Blender, and three.js. Meshy serves as one of its cloud 3D generation backends, using image-to-3D and text-to-3D to supply engine-ready characters and key props for several of the project's playable demos.

An Open Reference Pipeline for AI Game Creation

Bohan Zeng is a PhD student with the OpenDCAI group at Peking University and the project lead of 3AGameFactory. He sets the project's direction, designs its end-to-end technical framework, and coordinates asset generation, engine integration, agent workflows, and open-source collaboration.

3AGameFactory is a reference repository for AI game creation. A coding agent reads its skills, translates a game requirement into image, 3D, motion, audio, and CG-video tasks, then generates gameplay, UI, and engine code on top of the resulting assets. The framework covers UE5, Unity, Blender, and three.js.

What the project is not trying to prove is that a single model can make one impressive asset.

"The question isn't whether one model can create an impressive asset. It's whether these capabilities can form a reproducible, inspectable pipeline that works inside real engines."

The naming deserves a note. "3A" here refers to designing around the full capability stack a high-quality game requires — not a claim that today's generated results are ready for commercial AAA production. Rigging, motion, game feel, balancing, and complex scene generation all still have substantial room to improve, and the team is explicit about that.

The motivation came from a pattern Zeng kept noticing in AI game projects: a one-off generation demo presented as equivalent to complete game production, with no explanation of how assets actually enter an engine, connect to gameplay, get validated, or get repaired when they fail. 3AGameFactory is an attempt to publish an honest capability map instead — the skills, models, interfaces, and human judgment that AI game creation really requires, with the unsolved problems left visible.

Supporting four environments was a deliberate constraint rather than a feature list. Unity and UE5 are widely used for real-time games, Blender is valuable for asset processing, rigging, and offline validation, and three.js allows rapid browser-based publishing and testing. Covering all four forces asset interfaces, coordinate systems, scale, materials, and QA to be portable.

"Supporting multiple environments proves the workflow isn't a collection of scripts written for a single demo."

Why AI-Generated 3D Models Fail to Be Engine-Ready

Before Meshy entered the workflow, the hardest problem wasn't producing a 3D model. It was producing one that could survive the rest of the pipeline.

A single-view reconstruction might look convincing from the front while hiding holes or incorrect structure on the back. Models arrive with unknown scale, inconsistent orientation, fused parts, excessive polygon counts, or geometry that can't be rigged or imported reliably. Many of these problems only become fully visible once the asset is standing in a playable scene.

"The biggest difficulty was the gap between looking right and being genuinely usable. Some of these problems only show up once the asset is in a playable scene."

Automating that path is still harder. An agent-driven pipeline needs more than geometry and textures — it needs stable file formats, controllable polygon counts, correct scale and orientation, provenance records, predictable API behavior, and diagnostic reports when something fails. Characters add another layer: skeleton generation, skinning, motion retargeting, and in-engine animation validation.

For comparison, a traditional route to the same asset runs through modeling or sculpting, retopology, UVs, texturing, optimization, rigging, animation, format conversion, engine import, and testing. It usually involves several specialists and takes hours or days. Generative models can compress the distance from zero to a first testable version dramatically, but art direction, collision, animation quality, and gameplay integration still need people.

Choosing an Image-to-3D API an AI Agent Can Call

The 3AGameFactory team first heard about Meshy through a recommendation from a senior fellow student, alongside articles circulating on WeChat. At the time the team was systematically evaluating mainstream 3D generation services, looking specifically for a cloud API an agent could call reliably. Beyond the web application, Meshy offers a task-based API suited to automation, which made it a natural candidate as one of the project's backends.

The evaluation came down to five qualities: consistent output quality, controllable geometry and polygon count, complete PBR materials, a reliable API flow for submission, status checks and downloads, and compatibility with multiple engines. Predictable costs, diagnosable failures, and caching for repeated requests mattered just as much, because they determine whether an agent can run the pipeline sustainably rather than just once.

Several Meshy capabilities lined up with that list — image to 3D and text to 3D generation, low-poly and standard models, target polygon counts, remeshing, and PBR texturing, with direct export to GLB, FBX, OBJ, and USDZ.

GLB turned out to be the decisive format.

"GLB matters most to us because it connects to Unity, UE5, Blender, and three.js while packaging the mesh and its textures into a single file."

How Meshy Fits the AI Game Asset Pipeline

The coding agent first decomposes a game requirement into asset tasks, then decides for each asset whether to generate it, build it procedurally, or source it from an open asset library. Meshy is the backend selected for characters and a number of key props.

When Meshy is selected, the framework uses a unified wrapper to submit an image-to-3D or text-to-3D task through the Meshy API, poll its status, and download the GLB. The asset then goes through mesh cleanup, visual QA, a polygon-budget check, and scale validation. Approved props move into the engine-import pipeline. Characters continue through rigging, motion generation or acquisition, and retargeting before being combined with gameplay and UI code into a playable build.

Inputs are usually a reference image with a clear, fully visible subject, or a T-pose image for characters — though a text prompt describing the complete object also works. Parameters can include model version, target polygon count, topology, remeshing, textures and PBR, and output format. Every result lands in an artifact directory organized by game, run, and task, stored together with the task ID, elapsed time, credit usage, preview image, and mesh summary.

The division of labor between agent and human is drawn deliberately. Task submission, polling, downloading, caching, path management, basic cleanup, batch importing, and structured reporting are all automated. Developers still choose the references, prompts, and budgets, decide whether an asset should be regenerated, and make the final calls on appearance, rigging, motion, collision, game feel, and balance. Cost and API authorization also have to be confirmed explicitly before a paid backend is used for the first time.

Before an asset is allowed near a playable scene, the framework inspects it from multiple orthographic views: does it match the concept, is the back complete, does it stand upright, has an inferred ground plate been attached, does it exceed its polygon budget. Common inferred ground plates are removed automatically. The pipeline also handles scale, orientation, pivots, browser texture size, PBR binding, and engine-import reporting.

For characters, Meshy converts a clean T-pose reference into a textured character mesh. The team's own Puppeteer stage then predicts the skeleton and skinning weights. Motion comes either from MoMask or from a library such as Mixamo, after which a world-delta process in Blender retargets it to the character's skeleton and exports both a complete FBX and an animation-only FBX. Preserving vertex order between rigging and retargeting is a hard requirement, and each Puppeteer skeleton needs its own derived bone mapping.

Importing AI-Generated 3D Assets into Unity, UE5, Blender & three.js

Static assets are standardized as GLB with embedded textures. From there each environment takes a different route: Unity imports through glTFast and creates prefabs; UE5 uses Interchange/glTF or FBX and saves mesh, material, and texture packages; Blender imports, measures, and conditions the asset and can re-export GLB, FBX, or .blend; and three.js consumes GLB/glTF directly, with texture optimization for browser download and runtime performance. Animated characters generally enter through retargeted FBX or an already-rigged glTF workflow.

The recurring difficulty is that supposedly standard formats aren't uniform underneath.

"glTF uses Y-up, right-handed, meters. UE uses Z-up, left-handed, centimeters. That mismatch has to be handled every single time."

Unity needs an additional glTF importer. PBR materials, normal maps, and rendering pipelines can each produce a different look. On top of that the team had to sort out whether textures were actually bound, how triangle counts get reported under Nanite, character bone naming, vertex order for skinning, and the download and frame-rate budgets that three.js imposes.

From T-Pose Reference to a Playable Demo: AI 3D Character to Combat

The Unity two-player fighting demo shows the whole chain end to end.

The requirement was first decomposed into two characters, combat motions, a scene, gameplay, UI, VFX, and audio. The team prepared clean T-pose references for a muscular warrior and a ninja, then used Meshy to generate both characters as PBR-textured GLBs. Puppeteer rigged them, MoMask generated seven core motions for each fighter, and the clips were retargeted and imported into Unity. The agent then combined the character prefabs and animations with attack, blocking, energy, ultimate, round-timer, and HUD systems.

The result is a playable fighting demo in which Meshy supplied the key character assets while the complete experience came from coordinating several asset and code pipelines at once.

That coordination is what the 3AGameFactory team found genuinely surprising.

"The surprise wasn't that we could generate a character. It was that the character could pass through automatic rigging, motion retargeting, and Unity import, and then move, attack, and land an ultimate in real-time combat. Once a generated asset survives that whole chain, it stops being a showcase image."

Meshy assets appear across at least five of the repository's public demos: the Unity fighting demo's two characters, the UE5 fighting demo's player character, the UE5 RPG demo's character, stone tablet, and treasure chest, and generated objects in the Blender exploration and FPS demos.

The measured figures the team is willing to stand behind are development records rather than averages. One Meshy image-to-3D generation with PBR was clocked at roughly 283 seconds. One real test asset came out at 8.4 MB with 19,288 triangles and four embedded PBR textures, and imported into UE5 as six saved mesh, material, and texture assets. The Unity fighting demo contains two Meshy characters and 14 core motion tasks. The team has not yet run a controlled comparison against traditional manual production, and says so plainly.

Best Practices for an Automated 3D Game Asset Pipeline

Several habits ended up mattering more than any single model choice, and they transfer to anyone building an automated 3D game asset pipeline:

  • Content-hash caching. Identical requests hit the cache instead of being charged twice.

  • Disciplined polling. API calls use task polling, exponential backoff, and explicit terminal states rather than optimistic waits.

  • Clamped parameters and full provenance. Target polygon counts are clamped to the valid range; task IDs, elapsed time, credits, and preview URLs are all recorded.

  • Five-view QA. Generated assets are judged from five orthographic views, never from a single front render.

  • Bounded correction loops. Corrections stop after three attempts, or earlier on repetition, oscillation, or lack of progress.

  • Reports, not file checks. Each engine importer emits a structured report verifying triangles, dimensions, materials, and texture bindings.

"A file existing on disk is not success. The importer has to tell you the triangles, the dimensions, the materials, and whether the textures are actually bound."

For prototyping, the effect has been substantial. Characters and specific props that previously needed modeling — or repeated searching for suitably licensed assets — can now start as candidates generated from an image or a prompt. The unified API, GLB output, and engine-import scripts turn regeneration, QA, import, and playtesting into a short repeatable loop, and keeping the same asset ID lets the team swap an asset's appearance without touching gameplay code. That makes it far quicker to tell whether a problem originates in generation quality, import configuration, or the gameplay itself.

High-quality final assets still require human selection, correction, rigging review, collision setup, and art-direction alignment. Meshy shortens early acquisition and iteration; it doesn't remove production work.

More useful for the research question, it moved the framing.

"It let us stop asking whether we can generate a model, and start asking where the model still fails after it enters a game."

Where This Is Heading — and How to Join In

The 3AGameFactory team expects the next stage to shift from stacking model capabilities toward a verifiable production loop: an agent that understands requirements, selects tools, manages budgets, generates standardized intermediate artifacts, tests them inside an engine, and repairs failures based on structured reports.

Some problems look resistant to that approach. Skeleton quality, physical contact in motion, combat feel, numerical balance, and narrative consistency are all difficult for a general agent to improve through self-feedback, and will need specialized models plus long-term human refinement. Keeping those bottlenecks visible is part of the point.

"We want 3AGameFactory to keep exposing the real bottlenecks, and to become an open benchmark for the joint evolution of models, tools, and game engines."

Asked who should try Meshy, the 3AGameFactory team points to indie developers, technical artists, research teams, and tool builders — anyone who needs to validate 3D characters or props quickly, or who is building an automated content pipeline. The generation workflow is approachable, the API is easy to orchestrate, and the output formats suit further processing. Teams expecting an unmodified, commercial-quality final asset should still plan for human QA and post-processing.

3AGameFactory is open source under Apache 2.0 and available on GitHub. Contributors working on model wrappers, operators, or pipeline runners can start from the project's development harness, which includes a CPU-only smoke test path so you don't need model weights or a GPU to get going.
