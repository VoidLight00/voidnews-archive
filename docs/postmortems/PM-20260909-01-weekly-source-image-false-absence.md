# PM-20260909-01: 수집 실패를 출처 이미지 부재로 표시한 Weekly

## 1. 요약

외부 미리보기 수집 실패와 오래된 누락 목록이 겹쳐 실제 이미지가 있는 기사에 ‘출처 이미지 없음’이 표시됐습니다.
누락 316개 중 238개에 원문 이미지를 연결하고, 기존 0바이트 파일 1개를 제거했습니다. 현재 미리보기 미제공 79개는 조사 결과와 한계를 별도로 기록했습니다.
현재 데이터·실제 파일·원문별 근거를 검사하도록 바꾸고 브라우저의 수집 실패를 이미지 부재로 단정하지 않도록 수정했습니다.

## 2. 증상

사용자가 37주차에서 이미지 부재 표시를 지적했습니다. AlphaGenome Atlas와 항공기 비행운 기사 모두 실제 원문 상단 이미지가 있었습니다.
기존 검사는 과거 missing.json과 baseline만 비교해 신규 미해결 0건으로 통과했습니다. 현재 데이터에는 Weekly 927개 중 316개에 이미지 필드가 없었습니다.
이미지 파일을 연결한 후에도 대표 이미지가 회색 배경처럼 보였습니다. 파일 로드 성공만 검사하면 이 문제를 놓쳤습니다.

## 3. 타임라인

- 20:14 가설: 이미지 자체가 없는 기사다 → 시도: 현재 Weekly 데이터를 다시 집계하고 원문을 조회 → 결과: FAIL — 원문 이미지가 있는 최신 13개 모두 저장 필드가 없었습니다.
- 20:24 가설: 실제 이미지 파일을 연결하면 정상 표시된다 → 시도: 13개 이미지 로드 확인 후 화면 촬영 → 결과: FAIL — 대표 이미지가 밝은 배경과 screen 혼합 효과 때문에 거의 보이지 않았습니다.
- 20:25 가설: 이미지 표시 효과가 원인이다 → 시도: 불투명도 1과 일반 혼합으로 수정 → 결과: PASS — 데스크톱·모바일 화면에서 원문 그림이 보였습니다.
- 20:28 가설: 현재 기사와 조사 근거를 직접 연결해야 한다 → 시도: 317개 조사 기록과 파일 해시·실제 연결을 검사 → 결과: PASS — 238개 복구 이미지가 연결되고 79개 제한 항목이 분리됐습니다.
- 20:34 가설: 기존 회귀 검사와 게시 파일 검사도 새 상태를 따라야 한다 → 시도: 신규 근거 원장을 기존 근거와 함께 대조하고 삭제된 파일을 게시 검사 범위에서 제외 → 결과: PASS — close.sh 종료코드 0, GREEN입니다.

## 4. 근본 원인

이미지가 보이지 않은 직접 원인은 브라우저가 의존한 외부 미리보기 수집 실패였습니다. 실패 원인이 반환되지 않았는데도 화면은 이미지 부재라고 단정했습니다.
출처를 다시 수집하는 과정에서도 작성자 사진, 사이트 공통 표지, 다른 날짜의 변경 기록 이미지를 기사 이미지로 오인했습니다. 전역 body의 logo 배치 클래스 때문에 본문 전체를 제외하거나 article만 있는 페이지를 놓치는 경우도 있었습니다.
이 문제가 검사를 통과한 이유는 누락 검사 입력이 현재 게시 데이터가 아니라 과거 작업 파일이었기 때문입니다. 기존 집계 검사는 행 수 합계만 확인했고 실제 이미지 연결을 확인하지 않았습니다.
마지막으로 파일 존재·응답 성공을 화면 표시 성공과 동일시해 대표 이미지의 혼합 효과를 놓쳤습니다.

## 5. 관점 분석

- 기술: 수집 실패·확인된 부재·출처 미확정이 하나의 빈 값으로 합쳐졌습니다. 그림 선택 범위와 실제 화면 표시 검사도 부족했습니다.
- 프로세스: 오래된 누락 목록을 최신 데이터의 증거로 사용했고, 원문 확인과 화면 확인을 완료 조건으로 연결하지 않았습니다.
- AI협업: 이전 검사 통과 문구를 현재 이미지 상태의 증거로 받아들였습니다. 원문과 결과 화면을 대조한 뒤에만 완료를 보고해야 했습니다.

## 6. 해결

원문을 직접 조사하고 게시자가 제공한 기사 이미지 원본을 저장했습니다. 작성자 사진·사이트 장식·다른 기사 이미지를 제외하고, 동일 기사에 제공된 공유용 이미지는 별도 근거로 기록했습니다.
Weekly 두 종류의 카드 모두 저장된 이미지를 사용하도록 수정했습니다. 이미지 요청이 실패하면 미리보기 미제공으로 표시하며, 출처에 이미지가 없다고 단정하지 않습니다.
확인되지 않은 새 누락, 근거 없는 부재 주장, 연결되지 않은 복구 이미지, 변경된 파일 해시를 새 검사에서 차단합니다.

### 운영 사이트 확인 중 추가 발견: 한글 파일명

20:47 운영 사이트 브라우저 검사에서 13주차 카카오 이미지 1개가 HTTP 404를 반환했습니다. 전체 이미지 주소 794개를 조회한 결과 기존 이미지 32개의 주소가 HTTP 404였습니다. 32개 모두 실제 파일명은 한글 자모 분해형, 데이터의 주소는 한글 완성형이었습니다. Mac 파일 조회는 두 표기를 같은 파일로 처리해 로컬 검사가 통과했지만 운영 서버는 다르게 처리했습니다.

32개 이미지를 영문·숫자 파일명으로 복사하고 해당 Weekly 주소만 교체했습니다. 원본과 사본의 SHA-256이 일치합니다. `existingPathRepairs`에 이전 주소·새 주소·파일 해시·관측한 404를 기록했습니다. 다른 곳에서 사용할 수 있는 기존 파일은 보존했습니다.

검사는 파일이 열리는지만 보지 않고 디렉터리에 기록된 실제 이름과 주소의 대소문자·문자 구성을 정확히 대조하도록 보강했습니다. 한글과 같은 정규화 차이, 대소문자 차이를 재현하는 2개 실패 사례를 추가해 현재 이미지 회귀 검사는 15개이며 종료코드 0입니다. 운영 화면 검사도 실패한 회차와 누락 이미지 주소를 결과 파일에 기록합니다. 전체 운영 화면 재검사는 수정본 재배포 후 별도 결과에 기록합니다.

경로 수정본을 운영 사이트에 반영한 뒤 전체 25개 회차와 실패·모바일 사례를 포함한 32개 브라우저 검사가 종료코드 0으로 통과했습니다. 총 927개 기사 중 848개에서 이미지 로드를 확인했고, 79개 미제공 항목은 조사 상태를 그대로 표시했습니다.

사용자의 상시 필수 요청에 따라 기존 이미지 선택 610개를 변경 감시 기준으로 보존했습니다. 이 기준은 원문 의미 검증 완료라는 주장이 아닙니다. 신규 기사·경로 교체·동일 경로의 바이트 교체는 새 출처 조사 없이는 차단하며, 조사한 이미지가 실제 첫 썸네일인지도 검사합니다. 새 실패 사례를 포함한 회귀 검사는 19개입니다. 사이트 작업 지침과 운영 주소 확인 명령을 연결했습니다.

## 7. 재발 방지

`scripts/check-weekly-source-images.mjs`와 `references/weekly-source-image-audit.json`이 현재 기사·출처·이미지 해시를 대조합니다.
`scripts/test-weekly-source-images.mjs`는 오래된 빈 목록, 출처 변경, 403의 부재 오인, 잘못된 바이트를 실패 사례로 검증합니다.
`scripts/check-source-image-policy.mjs`는 저자 사진·전역 로고 클래스·article 범위·영상 정지 이미지 선택을 검증합니다.
`scripts/test-weekly-images-ui.mjs`는 25개 실제 회차의 카드와 이미지, 모바일 대표 이미지, 요청 실패 표시를 확인합니다.

## 8. 다음 세션 룰 후보

이미지 부재는 정상 원문과 해당 기사 범위를 확인한 결과로만 기록하고, 수집 실패·파일 존재·화면 표시를 서로 다른 증거로 검사합니다.
